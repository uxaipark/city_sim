# 추가 최적화 4·5·8·11 — 2026-09-27

## 최종 반영

- **5 — 차량 반복 작업 제거:** 도로별 격자 길이와 차선 시작점, 진입 도로·방향·차종별 경로 후보와 가중치를 캐시한다. 활성 차량 구간 배열을 재사용하고 비활성 고속도로 차량의 숨김 행렬은 새로 비활성화됐을 때만 쓴다. 점유 격자 생성을 별도 함수로 분리하고 셀 기록 함수를 차량마다 생성하지 않는다. 밀도가 같으면 밀도 설정을 반복하지 않는다.
- **8 — 변경 없는 값 재사용:** 시간이 같으면 하늘·태양·달·안개·가로등 색과 교통 밀도를 재계산하지 않는다. 하늘 돔은 카메라를 계속 따라가고 시간 유니폼을 사용하는 애니메이션은 유지한다. 그림자 투영 크기가 바뀔 때만 투영행렬을 갱신한다. HUD 값이 같으면 DOM 쓰기를 생략한다.
- **11 — 정적 그림자 캐시:** 정적 건물·도로·주차 차량·가로등·신호 기둥·지하철 출입구의 깊이를 별도 맵에 저장한다. 다음 프레임에는 이 깊이를 본 그림자 맵으로 복사한 뒤 차량·나무를 원래 깊이 검사로 그린다. PCF 필터는 결합된 하나의 깊이 맵에 그대로 적용한다. 나무·차량 수량, 메인 해상도, 그림자 해상도는 줄이지 않는다.

## 4번을 기본 코드에 반영하지 않은 이유

앞차 탐색용 비트 인덱스, 혼잡 시 첫 칸 즉시 조회, 활성 차선만 역순 스캔하는 다음 점유 칸 테이블을 비교했다. 현재 교통 상태에서는 짧은 탐색이 많아 인덱스 생성·조회 비용이 절감량보다 컸다. 비트 인덱스 회귀 실행은 평균 2.64 → 3.08ms로 느려졌다([실험 기록](traffic-index-rejected.json)). 다음 칸 테이블과 혼합 탐색도 이득을 확인하지 못했다. 따라서 최종 코드에는 기존 앞차 탐색을 유지하고 5번의 캐시만 반영했다.

## 캐시 범위와 비용

- 카메라가 움직여 그림자 범위가 바뀌거나 태양이 이동하면 즉시 기존 방식으로 렌더한다. 세 번 연속 같은 상태일 때 정적 캐시를 만든다. 시간 흐름·이동 중에는 캐시 재생성 비용을 반복해서 지불하지 않는다.
- 광원/그림자 투영행렬·크기, 카메라 레이어, 정적 물체의 가시성·월드 행렬·버퍼 버전·재질 상태 변경을 감지한다. 도시 구조를 수정하는 새 기능에서 감지되지 않는 변경을 넣는다면 `shadowCache.invalidate()`를 호출해야 한다.
- Three.js r186의 PCF 깊이 텍스처 경로에 한정한 어댑터다. 다른 버전/그림자 방식에서는 원래 렌더링을 사용한다. 컨텍스트 복원 시 캐시를 폐기한다.
- 4096×4096 RGBA8+32비트 깊이 캐시는 추가로 약 **128MiB**의 GPU 저장 공간을 사용한다(드라이버 부가 비용 제외). `?shadowCache=0`으로 캐시를 끄고 비교할 수 있다.

빌드와 기존 프로파일러 스케줄 검증을 통과했다. 기존 번들 크기 경고는 남아 있다.

[변경 전](before-45811-warm.json)은 조건마다 300프레임 준비 후 120프레임, [최종 변경 후](after-5811-final.json)는 네 조건을 두 번 순회한 마지막 순회에서 조건마다 60프레임 준비 후 120프레임을 기록했다. 두 실행의 준비 방식·누적 시뮬레이션 시간이 다르고 초기 컴파일 및 시스템 부하 변동도 있어, 엄격히 통제된 개선율로 해석하지 않는다. 모든 수집 구간의 숨김 프레임은 0이었다.
