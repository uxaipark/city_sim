# 도시 시뮬레이터 프로파일링 — 2026-09-27

현재 환경의 주 병목은 GPU 렌더링, 그중 블룸 후처리다. 낮 기본 화면의 평균 프레임 간격은 **49.04ms (20.39 FPS)**이고, 계측한 JavaScript 프레임 작업은 **9.83ms**다. 난수 교체보다 렌더링 최적화를 먼저 해야 한다.

## 측정 조건과 한계

- Apple M1 Pro, RAM 32GB, Chrome 153 / ANGLE Metal.
- CSS 화면 1344×836, DPR 2, 실제 렌더 버퍼 2688×1672, MSAA 4, 그림자 4096.
- 시드 7, 기본 카메라·오후 3시, 근거리, 오후 10시를 측정했다.
- 13개 조건마다 60프레임 준비 후 120프레임 측정. 저장된 모든 측정에서 탭은 보이는 상태였다.
- 카메라·시각·설정은 고정하지만 시뮬레이션 시간은 계속 진행한다. 기본 재측정은 21.45 FPS로, 수 퍼센트 변동이 있으므로 작은 차이는 과해석하면 안 된다.
- 최초 Metal GPU 타이머의 구간별 값은 전체 프레임과 일관되지 않아 판단에서 제외했다. 아래 결과는 **GPU 타이머를 끄고 측정한 requestAnimationFrame 간격**이다. 효과를 뺀 전후 차이를 정확한 GPU 패스 시간으로 해석하거나 서로 더해서는 안 된다.
- 일반 실행의 품질 설정은 이번 작업에서 바꾸지 않았다. 효과 제외는 비용을 찾기 위한 진단이며, 품질을 유지한 구현의 성능 개선을 보장하지 않는다.

## 우선순위 1: 블룸 해상도 설정

[src/main.js](../src/main.js)의 `innerWidth * pr` 렌더 타깃을 `EffectComposer`에 전달한 뒤, 설치된 Three.js의 `EffectComposer.addPass()`가 그 크기에 renderer pixel ratio를 다시 곱한다.

실측된 메인 타깃은 **2688×1672**다. 그런데 블룸 내부 입력 크기는 **5376×3344**, 두 블룸의 첫 밝기 추출 타깃은 각각 **2688×1672**다. 메인 해상도 기준으로 블룸을 설정하면 첫 타깃은 **1344×836**이므로 현재 픽셀 수는 이 기준의 4배다.

또한 `bloomWide` 생성자의 절반 크기가 `composer.addPass().setSize()`에서 덮어써져 두 블룸이 같은 크기로 실행된다. 초기화와 리사이즈의 크기 처리도 통일해야 한다.

메인 해상도·MSAA를 유지하고 블룸 크기만 메인 렌더 타깃 기준으로 설정한 실험은 **20.39 → 22.84 FPS**였다. 우선 이 크기 계산을 바로잡고 넓은 블룸의 해상도를 명시적으로 관리하는 것이 적절하다. 번짐 반경·밝기를 맞추고 낮·야간 이미지 비교를 해야 시각 품질 보존까지 확인할 수 있다.

## 나머지 GPU 최적화 후보

- **나무**: 제외 시 평균 프레임이 약 8.5ms 짧아졌다. 현재 수종별 인스턴스 묶음이 도시 전체에 걸쳐 있어 묶음 안 개별 나무는 자동 컬링되지 않는다. 공간별 묶음으로 나눠 카메라와 그림자 절두체별로 제외하는 방법을 먼저 비교할 수 있다. 나무 수·모형 품질을 줄일 필요는 없지만 draw call 증가를 함께 측정해야 한다.
- **스타버스트**: [src/postfx.js](../src/postfx.js)는 각 픽셀에서 원본 1회 + 4방향×14회, 총 57회 텍스처를 조회한다. 현재 해상도에서 프레임당 약 2.56억 번의 논리적 조회다. 밝기 추출 공유·영향 없는 영역 제외를 검토할 수 있다. 단순히 방향별 패스로 나누는 것만으로 조회 수가 줄지는 않는다.
- **그림자**: 정적 물체와 동적 차량 그림자를 구분해 캐시하는 방법이 후보이나, 태양·카메라·바람 변화 시 정확하게 무효화해야 한다.
- **자동 노출의 추가 장면 렌더**: 출력은 24×24라도 지오메트리를 다시 처리한다. 기본 렌더의 중앙값은 102 draw calls / 20,859,589 triangles이며 노출 측정 프레임에는 약 3,245만 삼각형이다. 출력 크기만 작다고 지오메트리 비용도 작아지지는 않는다.

## CPU 병목과 PRNG

| CPU 구간 | 원거리 낮 ms | 근거리 낮 ms |
|---|---:|---:|
| 차량 갱신 | 5.37 | 4.97 |
| 보행자 시뮬레이션 | 3.23 | 3.81 |
| 보행자 가시성 검사·GPU 배열 구성 | 0.00 | 2.70 |
| 신호등 | 0.27 | 0.29 |

- 차량 CPU 비용은 [src/traffic.js](../src/traffic.js)의 차선 점유 격자, 앞차 탐색·가감속·회전 처리와 행렬 작성에 집중된다.
- [src/people.js](../src/people.js)는 영역 밖 사람도 전체 배열에서 검사하며, 근거리 가시성 판정도 전체 인원을 순회한다. 도로·공간별 인원 인덱스를 두고 필요한 후보만 순회하는 것이 다음 CPU 최적화 후보다.
- 별도 Node/V8 샘플링에서 차량 `update` 자체는 약 44.4%, 보행자 `update` 자체는 약 36.1%였다. 하위 함수는 별도 노드다. 이 비율은 브라우저 전체 프레임 점유율이 아니다.
- PRNG는 평균 **230회/시뮬레이션 프레임**, `noise.js` 난수 함수의 샘플 점유율은 약 **0.08%**였다. 현재 Mulberry32 교체의 우선순위는 낮다. JIT 인라이닝과 샘플링 오차가 있어 정확한 독립 함수 시간으로 단정하지는 않는다.
- 근거리에서 보행자 렌더만 제외한 FPS 차이는 작다. 활성 인원 126,000명 중 화면에 그린 인원은 평균 690명이었다. 이 실험에서도 시뮬레이션과 가시성 계산은 유지했다.
